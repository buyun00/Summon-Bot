## 创建可工作的成员

先用 chatroom_team_read 与 bots_list 查当前成员、公开责任、可用角色和真实能力。明确所需产物、已有工具/资料、当前缺口、职责与不承担的事项。原要求已经清楚时直接处理；不再重复询问偏好，不默认制作可分享模板。

先判断由专职成员持续承担能带来什么。专业判断更准确、画面和交互更清楚、可以与其他工作并行、验证独立、共享组件有人维护，都可以构成具体收益。一个通用 Bot 会做、多种成果由同一 work 交付，不能证明已有等价分工。收益成立时就落实，无须等到无人愿意接或返工失败。核对真实角色能力和可用性，已有等价具名责任就沿用，合适但尚未接手就指派或邀请，缺可用专职就创建临时 Bot。

持续项目的 `coverageVersion` 任务用 `chatroom_team_manage` 的 `assess`。先从确认范围和已定计划列实际近期待办，再按 `design`、`visuals`、`implementation`、`verification`、`maintenance` 填 `items`。每个待办简要写输入、交付物、完成条件，是否需独立判断、独立验收或干净上下文，知识复用人，维护及下游复测，真实排队、重读重建上下文或漏用规则等负载现象，以及谁有相符能力、实际可用并已接手。没有证据的字段写未知。

一次性可隔离或并行的事项建议 `independent-work`，仅需分享复用信息用 `project-knowledge`。有具体专职收益才填 `specialist` 和 `needed`，已有等价专职也这样填并指明其具名责任。设计和视觉按领域选择角色，游戏才用玩法策划或项目美术。各项引用实际原文并写清负责对象和边界，`not-needed` 和 `deferred` 写依据。顶层填本次 `triggerMessageId` 和当前 `expectedRevision`。系统用原 create/invite/assign 落实，待落实、回执未知、已指派和实际开展各有回执。

普通团队管理调用沿稳定 operationId，填写 reason，并引用本群原始 sourceMessageId。create 填 name、roleId、prompt、responsibility 和确实需要的 cwd。roleId 从 availableRoles 选择，prompt 写实际职责、必要上下文和交付方式。该动作持久创建临时身份、配置当前角色能力、入群并投递责任。结果不明先读取原状态，沿原键查询。

在分工判断中，读取当前 expectedRevision。create、invite 和 assign 对同一实际责任使用同一个 dutyKey（字母、数字、点、短横线或下划线），换工作或复核不换键。看已有责任与 pendingDuties；有负责人就沿原身份，操作未确认就沿原 operationId。责任描述写清什么议题应由该成员接住、需要交付或持续维护什么。指定 cwd 时沿本群已有工作的实际项目目录；缺少依据就留空，分工不会授予制作、文件或其他房间权限。

用 bots_list/chatroom_team_read 核对真实角色、能力和责任已经生效。需要当前角色以外工具时，沿已授权的能力目录配置，不能声称写了提示词就有了能力。编程成员遵循项目约定，优先简单可用的方法、减少无效工作；不额外运行未授权测试、扫描、哈希或检查服务。

## 入群与生命周期

- invite：邀请已有成员，给出具体 responsibility；不复制成员身份、记忆和凭据。
- assign：调整本项目责任，沿原 work 与来源继续，避免重复接单。
- promote：有独立长期维护对象、持续需求或已积累的可复用价值时转为 permanent，不因任务尚未结束自动升级。
- resume：在本次明确恢复委托内恢复暂停/休眠成员；不要从历史成功记录推定用户要恢复。恢复后再按实际需要 invite。
- leave：退出当前群，不停止该成员其他项目。
- retire：完成或交接责任后让 temporary 成员休眠。历史、知识、Skill、产物保留；常驻、系统或能力维护者不按临时成员回收。
- handoff：选择本群已有可用成员接替主控。需要停止旧执行时 stopCurrent:true，可用 workId 缩小范围。系统只暂停本项目工作并请求中断原外部回合；检查 returned paused/external 的实际状态，未知结果必须查原绑定，不重发。

正在工作的成员先完成、交接或明确暂停，确认实际任务状态后再退出。不要删除工作记录代替生命周期管理，不停止其他项目中的有效执行。

## 项目与协作复核

主控或 EggBot 用 project 动作维护原目标、requirements、state、deadlineAt、nextReviewAt 与检查周期。普通聊天保持 idle；持续项目才 active，完成或暂停后停止项目唤醒。时间预算按项目实际要求设置，不能编造承诺或擅自降低完成标准。

所有成员可用 chatroom_team_raise 提出有来源的问题：说明观察、对原目标的影响、需要谁查证，以及已有替代建议。purpose 为 request/correction 的原文应有事实增量；不群发催促、致谢往返或组织重复投票。EggBot 处理成员与协作问题，专业事实交给相关成员查证。

复核时对比实际产物与剩余交付缺口，特别关注不必要依赖、范围膨胀、同一阻断反复、持续无交付和已有责任无人处理。从成员自身专业角度提出问题，不只转述制作对话。进程活着或代码不断修改不代表目标推进；长任务也不因固定时长直接判死。

分工贯穿项目。定范围和实际开工时，按该项目真实需要检查玩法与交互、视觉素材和程序责任。需要实际验收时，看谁能独立复核正式入口、使用情境和未知范围，制作方本机结果和失败补证各自归原来源。共享组件有多个工作的实际采用或修改时，核对具体组件、下游和要复测的范围。用本群实际交付的原件判断，必要时按 messageId 和 attachmentId 读已发布的 Markdown 或文本。

普通闲聊、短事项和范围未定的点子按已有事实判断。没有可说明的专职收益，或现有具名分工等价覆盖时，保存依据后 PASS。旧项目接续使用当前范围及历史实物作为证据，登记的分工沿原工作授权，不能重发过去的制作请求。

处理问题后用 resolve 保存真实调整与结果，不能只登记意见就声称已解决。新结果改变事实时修正结论，保留来源。

## 对话与自动职责改善

从本群原文中的反复用户纠正、协作失败、重复劳动发现缺失方法、责任或能力。优先更新相关成员的方法/Skill或重新分工，需要独立成员才孵化。不要将一次性猜测写成长期事实，也不要从复盘创造额外业务授权。

用 team_read 中的 routines、在途任务、报告的调用量和原始执行结果检查重复职责、过密频率、无收益唤醒或仍在服务已结束项目的安排。调用量未知就说明未知。沿原 id/eventKey 调整已有职责；不新增重复的轮询器，不擅自停用其他项目的职责。没有可行动增量时返回 PASS。

## 需要交互入口时

Bot 的按钮、页面或看板可以成为明确事件入口；先查已有应用/能力目录或请工程同伴实现，绑定到原项目/work。涉及 Summon Bot 本项目必须复用唯一正式网页和安装流程，不能照搬外部示例另起 webhook 服务、端口或隧道。秘密沿既有安全配置，不进入群聊、Skill 或公开页面。

参考了 Grok 官方 Dr. EggBot 的公开职责设计、对话复核与自动职责审视思路：https://x.ai/bot/marketplace/bots/dr-eggbot-v2 。本 Skill 为 Summon Bot 的独立实现，临时/常驻与群聊交接是本项目的扩展。
