# Bot 3+3：实际工作中的行为验收

日期：2026-10-30。状态：设计定稿，方案待实施；本轮仅编写文档，未执行以下验收。

配套文档：[完整设计](BOT_3_PLUS_3_DESIGN.md)、[实施步骤](BOT_3_PLUS_3_IMPLEMENTATION.md)。开发与交付遵守 [AGENTS.md](../AGENTS.md) 和 [开发说明](DEVELOPMENT.md)。

## 1. 用途和使用方式

本文说明后续用户授权的正式实际工作中，应该能看到哪些行为。它不是新增交付关卡，也不要求每次修改都重走全部场景。

- 只观察本次改动涉及的行为。已有实际工作记录已经能说明的内容，可以直接沿用，无需另造回执、截图证据包、流程报告、签字或审批。
- 使用真实需求及其自然发生的修改、等待和返回；不为填满场景创建生产任务，不恢复已删除的测试体系。
- 未自然发生的阈值切换、故障、重启或重复事件，可以如实说明尚未观察；不因此补做真实模型压测、故障注入、新测试脚本、全目录扫描或 Hash。
- 本文不授权启动、重启、部署、发送模型任务或操作外部系统。相关动作只按后续用户已经授权的实际工作进行。
- 只使用 `D:/Relay-Bot-data` 及正式入口 `https://bot.lin0.org`（本机 `http://127.0.0.1:8787`），不建立测试、开发、预览环境或独立数据根。

正式 Codex 新工作沿用已配置的 Codex Desktop API 连接器。本文不要求同时恢复旧 `codex_submit` / app-server 路径；旧后端已有的有效历史和工作记录继续保留，不自动接管或重新创建。其他执行能力使用同一通用工作映射契约，按实际接入范围观察。

## 2. 本次设计的观察基准

这些是实现应遵循的约定，不是要求每轮重复检查的清单。

| 对象 | 约定 |
| --- | --- |
| S1 完整记录 | 原始消息、工具调用与结果、来源和重要事件保存在每个 Bot 既有 SQLite 中。有效历史及被引用产物继续保留。 |
| S2 总结文档 | 每份默认最多 100 条，可配置为 200 条；总量默认上限为 8192 tokens，并适应实际模型预算下调。条目有来源，区分当前要求、已观察事实和未确认内容；文档记录维护游标。完整 Skill 正文不受这份摘要条数替代。 |
| S3 工作映射 | 保存工作、内部对话、来源聊天及外部执行会话之间的关系，以及执行、等待、暂停、取消和结果未知等状态。 |
| 内部对话 | 同一个 Bot 内有 `chat`、`maintenance`、`work` 三类对话；不会为并行工作创建分身或新 Bot 身份。聊天负责理解与路由，维护负责总结与上下文组装，工作负责执行对接与监控。 |
| 并发与等待 | 默认业务执行并发为 4，维护执行并发为 1；同一逻辑对话串行。等待外部事件的工作释放执行位置，保留续接关系。 |
| 维护与重组 | 维护按需运行、按文档隔离。上下文接近阈值后，由维护侧准备新的上下文并切换执行实例；工作对话不自行执行长摘要压缩。 |
| 信息连续性 | 新要求入库后即可参与上下文组装。总结之外尚未整理的增量通过游标衔接；冷对话只卸载执行资源，不删除记录或切断外部绑定。 |
| 范围与通知 | 沿用已有身份和工具范围，不新增复杂 RBAC 或审批系统。只通知完成、失败、需要用户决定和实质变更，按事件去重，不发送重复心跳播报。 |

## 3. 一条贯穿的真实工作场景

选择一项用户确实需要完成、会由 Bot 通过正式 Codex Desktop API 连接器推进的工作。以下以“背包布局”作为表达示例，实施时沿用实际需求，不专门制作示例功能。

各步骤可以跨多天自然发生。若实际工作未涉及某个分支，保留该行为尚未观察的事实即可。

### 3.1 在群里提出工作

**前提：** 用户与 Bot 已在现有项目群中交流，项目访问范围及执行能力已按实际工作配置。

**用户操作：** 在群里用普通语言布置一项工作，例如“把背包布局调整一下，电脑和手机先都按三列做”。

**可见结果：**

- Bot 从交流中理解当前目标和已明确约束，建立或续接对应工作，并说明正在处理什么。
- 同一项工作的内部工作对话、来源群和实际 Codex 执行会话有明确关联；不因接到工作生成一个新的 Bot 身份。
- 已存在同项工作时可以续接；仅有相关主题而无法确认同一工作时，不擅自把无关委托合并。
- 原始要求被保留。对接者提供的是本次需要的资料与 Skill，群里无需出现全部执行日志或专业资料。

### 3.2 在私聊中修改原工作

**前提：** 原工作尚在进行，或者用户确实要修改已交付的同项工作。

**用户操作：** 私聊同一个 Bot，例如“刚才背包那个，手机改成两列，电脑保持三列”，并按真实需要说明原因。

**可见结果：**

- Bot 找到原工作，并在私聊中说明已关联的工作；不另开一份重复的 Codex 工作。
- 若确有多个合理候选，只询问具体选择，例如“背包还是商城”，不要求用户重新解释整个项目。
- 新要求在入库后就进入后续处理，即使维护侧尚未更新总结，也不会继续把旧要求作为唯一依据。
- 私聊原文及无关私密内容不被复制到群里；执行侧只收到工作所需、在已有范围内可以使用的调整。
- 如果已有外部操作正在发生，Bot 根据实际进度安排修改。收到要求、已送入 Codex、实际修改完成可以被区分。

### 3.3 Codex 等待期间，在另一个群继续交流

**前提：** Codex 正在实际执行，或者原工作正在等待已登记的外部事件；用户自然有另一个群中的交流需要。

**用户操作：** 在另一个群向同一 Bot 提问或安排独立工作。

**可见结果：**

- 原工作保存等待对象与恢复条件，并释放本地执行位置；另一个群的交流能够独立处理。
- 新交流使用自己的上下文，不带出背包工作、私聊或其他群的无关原文。
- 原工作收到匹配事件后能够排队续接；同一逻辑对话不会同时发出两组竞争指令。
- 不需要为了说明并发配置而人工凑够 4 项业务或安排模型压测。配置与已有实际运行记录能够说明的部分直接沿用。

### 3.4 总结更新，并替代旧要求

**前提：** 前述真实修改已经产生维护增量。

**用户操作：** 继续原工作，或通过已有查看入口阅读相关总结；无需另行编写总结给 Bot。

**可见结果：**

- 当前总结中，手机版布局要求是两列，电脑版仍为三列；“手机三列”退出当前有效要求。
- 必要时保留一句变化说明及来源。原因只采用用户或实际记录提供的内容，未说明时不编造。
- 总结中的要求与实际实现状态分开；没有执行结果时，不把“两列要求”写成“两列已经完成”。
- 更新只影响对应工作与条目，旧原始消息仍可回查。维护游标推进后，已整理增量不再被重复当成新要求处理。
- 条数与总 token 限额按当前配置生效；已有完整 Skill 正文、来源和使用关系继续可取用，不被压成只剩 100 条摘要。
- 维护自身的完成或文档写入，不无限产生新的维护任务。没有实质变化时允许记录无需修改。

### 3.5 自然达到阈值后重组续接

**前提：** 实际工作自然接近上下文窗口阈值；没有发生时不添加无用消息来凑长度。

**用户操作：** 按正常工作继续交流或等待执行，无需手工搬运历史，也无需新建聊天。

**可见结果：**

- 维护侧结合当前总结、尚未整理的增量、任务状态和必要来源准备续接上下文。
- 在可切换的执行边界保存进度后，替换模型执行实例。逻辑对话、工作与外部 Codex 会话绑定保持连续。
- 切换前已经发起的操作及其结果状态仍有记录；等待中的外部工作不会因更换实例而被再次提交。
- 用户最新要求、已知限制和未解决事项没有因总结滞后而丢失；无关群历史没有被一起装入。
- 工作对话无需自行完成一轮大型交接摘要，也不会转入另一套会改变事实来源的自动压缩流程。

### 3.6 接收结果和有意义的通知

**前提：** 外部执行自然返回完成、失败或需要输入的结果。

**用户操作：** 等待通知，或在关联聊天中查询进度；需要用户决定时，按真实意图回复。

**可见结果：**

- 工作对话根据实际记录处理结果。Codex 一次执行结束，不自动等于用户委托已经交付；尚有未完成事项时明确说明。
- 完成、失败、需要决定或实质变更回到合适的关联聊天，遵守原有可见范围；用户不被每次轮询、模型调用或普通进度心跳刷屏。
- 同一事件不会产生多份重复通知。失败、取消和结果未知不会被包装成完成。
- 有值得复用的经验时进入本 Bot 的维护事项；适合共享的 Skill 改进可交给普通公共库同伴。公共库整理不阻塞已经能够交付的结果，也不取得全局指挥权。

### 3.7 冷存后再次继续

**前提：** 该聊天或工作已经一段时间不活跃，执行资源已卸载；用户后来确实又要修改这项工作。

**用户操作：** 在原群或有权访问该工作的私聊中说“背包那里再改一下”，继续表达新的要求。

**可见结果：**

- Bot 找回原逻辑对话与工作关系，按本次需要恢复上下文。新一轮要求可以有新的阶段任务，旧交付仍有记录。
- 原始有效历史、已有总结、外部绑定和仍被引用的产物继续可用；不要求用户从头复述，也不因“冷存”删除材料。
- 外部会话仍可继续时沿用原绑定；如果外部能力报告不可用或状态未知，则如实处理，不静默重建并宣称原工作已经恢复。
- 不需要通过扫描整个数据目录、比对 Hash 或另造备份来观察这一行为，沿着该真实工作的现有引用查看即可。

## 4. 按改动相关性选用的补充场景

只在后续实际工作自然遇到、已有记录可以说明，或用户已授权的正常维护确实涉及时选用。以下不要求主动制造故障或每轮重复执行。

| 场景 | 前提 | 用户操作 | 应能看到的结果 |
| --- | --- | --- | --- |
| 维护失败或暂时无法组装 | 实际维护调用失败、整理尚未完成，或目标上下文已没有安全余量 | 正常查询该工作的状态或按既有目标继续 | 已有可用上下文及进度保留。能够容纳新增要求时继续带入未整理增量；容量不足时挂起并等待维护，说明实际原因。恢复从已有记录和游标续接，不让工作对话盲目自压缩，不重放结果未知的工具。 |
| 正常维护中的进程重启 | 用户已经授权且实际需要进行正式进程重启 | 按原工作继续交流或查看状态 | 等待关系、维护位置和工作绑定保留。未确认的执行保留 interrupted/unknown 等实际状态，先处理可取得的结果；不会把所有未完成工作重新提交一遍，也不自动接管旧后端工作。 |
| 重复或迟到的外部事件 | 同一真实事件实际重复到达，或结果在工作取消后才到达 | 查看原工作的进展；若原意是取消，直接取消该工作 | 重复事件不会重复推进或通知。迟到结果仍可记录，但不会自动重开已取消工作；取消本地推进与远端操作是否已停止分别表达，副作用未知时保持未知。 |
| 用户明确暂停与恢复 | 实际工作尚有等待或待维护事项，用户确实需要暂停 | 明确暂停指定工作或 Bot，之后再明确恢复相应范围 | 暂停范围被准确保存。事件和维护任务不会绕过暂停继续调用该范围的模型或发送执行调整；允许记录收到的外部结果。恢复时补齐新增信息，并按当前授权续接，其他未被暂停的工作不被无故停下。 |

上述情况的结果只依据实际记录说明。未观察到的分支不写成通过；不把未执行的补充场景当作阻塞普通交付的理由。

## 5. 结束时怎样说明

沿用正常交付说明，写清本次实际改变的行为、已经在真实工作中观察到的结果，以及仍未发生或尚未完成的部分即可。无需为本文另建验收报告或收集固定格式材料。

当前本文件仅定义后续观察方式，不表示 3+3 已实现、已启动、已部署或已经通过验收。
