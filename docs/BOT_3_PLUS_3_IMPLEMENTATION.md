## 1. 实施对象与当前基础

本次改造的是单个 Bot 的会话、上下文和工作持续性。Bot 仍是独立 Pi Agent 本体；Codex 是按需使用的外部执行能力。内部多会话共享这个 Bot 的身份和积累，不创建任务分身，不建立全局模型主控。

以下依据 2026-10-30 读取的工作区源码与运行说明，不代表对正式安装状态的验证。相关文件已有未提交修改，实施时应以届时实际文件为基线，保留其他工作的增量。

## 2. 本轮统一契约

完整字段定义以主设计为准，以下是实施时不得拆开的边界。

### 2.1 数据与标识

- 每个 Bot 继续使用自己的既有 `state.sqlite`。S1 原始记录、S2 总结文档、S3 工作映射是该库内的三个维护部分，不分别建立数据库、服务或独立数据根。
- `botId`、`conversationId`、`workId` 长期稳定。`runId` 和 `contextGeneration` 表示一次执行及上下文代次，结束或替换它们不删除逻辑会话、工作或外部执行会话。
- S1 保留实际接收和产生的消息、工具调用与结果、状态事件以及来源引用。原始大输出和附件可以继续保存在现有产物目录，SQLite 保存稳定引用。
- S2 默认每份最多 100 条，可配置为 200 条；同时采用 `maxSummaryTokens = 8192`。当前模型实际可用输入预算不足时下调，不能把 8192 当作必须占满的配额。
- S2 正文可用 Markdown，但条目需要稳定 ID；文档需要来源消息引用、整数 `revision` 和 `throughSeq`。正文在 SQLite 中持有一份权威版本，不增加一套无同步保证的文件正文。
- S3 保存当前工作责任、工作对话、来源聊天、外部会话绑定、等待条件、未确认操作与待通知事项。工作状态、某次 Bot 执行状态、Codex 实际状态分别表达。
- 消息与操作沿用简单稳定 ID 去重；并发写入使用 SQLite 事务和整数修订检查。新关联使用记录 ID、消息 ID、执行 ID 与上下文代次，不新增内容哈希、签名或完整性流程。被本次改造直接替代的旧 digest 关联改为稳定引用；已有历史哈希原样保留，不重算、不比较，也不扩展成全仓去哈希工程。

### 2.2 三类内部对话

- `chat`：理解用户和同伴意图，查询候选工作，决定继续、新建或关联哪项工作，决定适当的回复对象和内容。
- `maintenance`：专职维护 S2，并为指定聊天或工作组装上下文。按文档或工作分批处理，结束一批即释放执行状态。
- `work`：承担明确委托，调用外部执行能力，理解进度和异常，推进下一步并汇报真实结果。

程序只执行已确定的存储、查询、投递、事件关联、身份检查和模型执行动作。相关性、语义路由、总结取舍和工作判断由相应对话完成。普通程序对确定参数进行范围、版本、容量和身份检查，不由提示词自行扩展工具权限。

### 2.3 调度与重组

- 默认最多 4 个业务会话执行位，加 1 个独立维护执行位；同一个逻辑会话始终串行。等待、暂停和封存状态不持续调用模型。
- 独立维护执行位避免业务会话全部占满后，重组请求无法获得处理。它只属于当前 Bot，不构成全局调度主控。
- 常规主执行不再调用 Pi 自总结压缩。接近实际上下文预算时，持久保存当前执行位置，由维护对话补齐总结和上下文包，再在安全工具边界创建新的执行实例。
- 维护失败时保留上一份可用总结、旧上下文视图和未处理增量；仍能容纳当前请求时使用这些材料继续。空间不足时明确挂起，等待维护恢复或输入缩小，不悄悄退回 Pi 自动压缩。
- 已发出的工具、消息和 Codex 操作不因上下文重建而再次执行。结果未知保留 `unknown` 等明确状态，先核对原操作记录与实际外部状态。

## 3. 最短可运行路径

以下六步是同一次交付的实现顺序，不是六套环境，也不要求每步建立测试、报告或单独发布。先接通必要行为，再按现有正式安装流程一次切换；不保留新旧机制并行运行。

| 顺序 | 主要工作 | 完成后应有的行为 | 依赖 |
| --- | --- | --- | --- |
| 1 | S1/S2/S3 与稳定关联 | 对话、工作、执行段、总结和外部绑定各有明确记录 | 现有 Bot SQLite |
| 2 | 单 Bot 多会话执行与持久等待 | 多个聊天和工作可并行，等待释放执行位，重启保留责任 | 第 1 步 |
| 3 | 维护与上下文组装 | 限额总结按增量更新，主执行可重组续接，无双套摘要 | 第 1、2 步 |
| 4 | 聊天语义路由与跨会话续接 | 群里提出、私聊修改能落到同一工作；有歧义才澄清 | 第 1～3 步 |
| 5 | 外部工作、事件续接和通知 | Codex 进度进入工作会话，完成和异常可自动回到相关聊天 | 第 1～4 步及既有桌面连接器 |
| 6 | 一次性转换、正式切换和清理 | 有效历史保留，运行引用全部更新，旧分身和旧压缩入口退出 | 前述必要行为连通 |

## 4. 各步的代码落点与行为

下列新增模块名是候选划分，不要求为了目录整齐创建空文件。实施可在同一职责内合并文件；接口与行为遵循主设计。

### 4.1 第一步：先建立可继续使用的数据记录

**代码候选**：`bot/src/storage/store.mjs`；必要时增加 `bot/src/storage/conversations.mjs`、`summaries.mjs`、`works.mjs`。继续使用现有 SQLite 连接与事务，不新增存储服务。

需要完成：

1. 保留消息与原始工具记录，给内部对话、工作和执行段建立稳定关联。S1 中每个可整理事件有可定位的顺序位置。
2. 将现有“每条消息一个 task，taskId 等于 runId”拆成清楚的概念。消息触发一次处理，并不必然创建长期工作；一次工作可由多个执行段持续推进。
3. 为总结文档提供读取、带修订更新、条目替换/合并/删除和来源回查。删除失效总结条目不删除 S1 原文。
4. 为工作提供记录当前要求、阶段任务、等待对象、外部绑定和待通知事项的接口。外部状态带观测时间及未知/过期信息，不能根据总结中的“完成”改写执行事实。
5. 让事件入箱、等待登记和待通知记录持久化。按稳定关联处理先到结果与重复事件，避免“结果先返回，等待后登记”导致永久遗漏。
6. 提供按已有 Bot 身份、会话、工作、来源消息和关键词的有限查询。复用当前身份与数据访问边界，不建设新的企业权限系统或向量服务。

**完成行为**：一个聊天消息可以关联已有工作，也可以只形成一次交流；工作等待与总结维护不会因主模型上下文释放而丢失。S2 可以被重建，S3 不依赖模型从摘要推测状态。

### 4.2 第二步：改造单 Bot 内部执行与恢复

**代码候选**：`bot/src/runtime/bot.mjs`、`bot/src/runtime/config.mjs`、`bot/src/agent/engine.mjs`、`bot/src/runtime/capability-updates.mjs`；可增加 `bot/src/runtime/conversations.mjs`。

需要完成：

1. 将共享的单个 Agent 可变状态改为每个活动执行实例独立持有消息、工具声明、回调、取消信号和用量。业务会话可并行，不能同时修改同一个 `agent.state.messages`。
2. 将单全局串行链改成同会话串行的本地调度，落实业务 4 个与维护 1 个执行位。没有可处理事件时不调用模型。
3. 工作进入持久等待后结束当前执行段、释放执行位。相关事件到达后恢复原工作，不靠模型循环等待或在一个长 `tasks_get` 调用中占住全部调度。
4. 保留用户暂停、取消及 Bot 停止意图。暂停工作仍可接收并保存结果，不能被迟到事件自动恢复；取消外部工作时分别记录请求和实际结果。
5. 重启时将丢失执行实例的 `run` 标为中断，保留其逻辑对话、工作、等待条件和待通知事项。已登记等待恢复订阅；可处理的已知事件重新进入原会话；有不明副作用的执行先核对。
6. 能力切换仍在安全边界完成。多个活动会话均需结束旧工具调用或明确保存其在途状态，不能继续按旧的 `this.active` 单实例假设判断整个 Bot 已空闲。

**完成行为**：一个 Bot 在群 A 聊天、群 B 聊天及跟进工作时拥有独立上下文。任一工作等待同伴或 Codex，不阻塞其他会话；维护始终有自己的可用执行位。Bot 被停止时保存责任，普通关闭客户端不停止这些工作。

### 4.3 第三步：接通独立维护和上下文重组

**代码候选**：`bot/src/context/context.mjs`、`bot/src/context/recovery.mjs`、`bot/src/context/resources.mjs`、`bot/src/capabilities/core-tools.mjs`、`bot/src/agent/engine.mjs`、`bot/src/pi/core/session-manager.mjs`；可增加 `bot/src/context/maintenance.mjs`、`assembly.mjs`。

需要完成：

1. 将总结编辑和上下文准备提供给 `maintenance` 对话，输入限定为目标文档/工作、当前总结、尚未整理的原始增量及本次请求。大量增量分批读取，不一次灌入全部历史。
2. 总结按稳定条目更新当前状态。保留必要的“之前是什么、现在是什么、原因和来源”，合并已无当前用途的中间过程。用户未说明原因时不补造原因。
3. 一批提交同时更新文档 `revision` 和确实覆盖的 `throughSeq`。若期间有新消息，保留为未处理增量；遇到修订冲突重读相关条目，不覆盖更新后的要求。
4. 维护自己的读取日志、总结更新事件和上下文包生成事件不再次自动产生同样的维护任务。一次真实业务变化可合并待整理事项，维护不无限唤醒自身。
5. 上下文包包括适用身份/规则、当前触发、有效要求、结构化工作状态、相关总结、未整理的必要增量及来源入口。维护模型选择材料；程序落实已有访问范围、代次、修订和容量限制。
6. 不把摘要当作授权。来源身份和工具允许范围仍取可信运行时记录。原文中的用户消息、同伴建议、工具结果和历史要求保持各自来源。
7. 使用模型真实窗口和必要输出空间计算可用预算。`maxSummaryTokens = 8192` 是总结上限；工具声明、输入、输出预留和其他必要材料不足时，相应缩小总结与增量批次。
8. 在未开始新的外部副作用、已返回工具结果落盘的边界切换。未决工具调用可继续由原执行持有至结束；确需释放时，先登记在途引用和结果未知状态，确保晚到结果回到原工作。
9. 主业务执行移除对 `PiCompactionLifecycle` 自总结链的调用，替换相应预请求和溢出处理。可以保留必要的模型传输重试、令牌估算和工具消息修复，但它们不能另起第二套摘要恢复路径。
10. 短期维护失败保留旧视图和增量；超出可用空间时进入可恢复等待。不能静默丢弃当前要求、删除原始消息或重启一项相同外部工作以绕过错误。
11. 完整 Skill 及相关资源继续在既有资源目录中维护和读取。总结可引用 Skill 和必要要点，不把 100 条总结当成全部专业知识库。

**完成行为**：工作对话无需自行阅读大量旧群历史来恢复注意力。达到重组条件时，新 `runId/contextGeneration` 继续原 `conversationId/workId`；历史、授权、工具结果和 Codex 绑定保持。维护执行每批独立装配，不累积成一个永不结束的全 Bot 巨型上下文。

### 4.4 第四步：让聊天对话决定工作归属

**代码候选**：`bot/src/capabilities/core-tools.mjs`、`bot/src/runtime/bot.mjs`、`capabilities/chatroom/service.mjs`、`capabilities/gateway/tools.mjs`、`roles/common.md`、`roles/protocol.md` 与相关 `roles/*/profile.md`。

需要完成：

1. 将现有房间/私聊来源和直连来源绑定为稳定聊天对话。传输负责确定来源标识；是否需要执行、关联何项工作由聊天对话判断。
2. 提供查询候选工作、请求维护层准备背景、建立工作关联、新建工作对话、向原工作提交修改的最小内部能力。
3. 明确引用或回复关系可直接定位；缺少关联时由模型结合项目、对象、来源和当前讨论查找候选。确有多个合理候选才向用户澄清，不以最后活跃或相似度最高自动执行修改。
4. 同一工作可以关联多个聊天，但只有一个当前负责推进的工作对话。来自群聊与私聊的要求保留原始来源、目标和授权范围；私聊原文不自动公开到群。
5. 闲聊、解释和短查询留在聊天对话；明确的持续工作才建立工作记录。任务完成后的后续修改可以形成新阶段任务，继续原工作对话，无需复制 Bot 身份或全部历史。
6. 调整模板与协议，使聊天、维护、工作对话只接收当前职责所需的指令。公开简介、内部规则和任务专属要求分别装载，避免三类提示词全量叠加。
7. 网页/原生端只消费必要的真实状态和关联字段。新建内部会话不必生成一个新联系人；保留群聊成员身份、来源引用和相关工作入口，不重做整个界面。

**完成行为**：用户在群里提出背包任务，随后私聊修改，能够续接同一工作。维护层准备相关背景，聊天层决定交给谁，工作层根据实际执行状态处理修改；其他无关群的历史不进入该工作。

### 4.5 第五步：接通外部执行、恢复与主动通知

**代码候选**：`capabilities/codex/executor.mjs`、`capabilities/services/builtin.mjs`、`capabilities/gateway/index.mjs`、`capabilities/gateway/tools.mjs`、`capabilities/chatroom/service.mjs`、`bot/src/runtime/bot.mjs`；沿用 `connectors/codex-desktop-api/src/server.js`、`broker.js`、`store.js` 及 `skills/codex-desktop-api/scripts/client.mjs` 的现有协议。必要时在现有 Codex 能力目录增加一个薄桌面适配模块，不另建后端平台。

新工作以当前 Codex Desktop 连接器为唯一默认执行路径。现有角色与 Skill 已禁止新建旧 `codex_submit` / app-server 工作；本轮不恢复它们、不做双后端自动选择，也不为 Desktop 不可用增加旧服务兜底。

需要完成：

1. 在外部创建/继续前保存 S3 工作、目标连接/主机/项目和本次稳定操作 ID。写请求超时后查询原操作，不换 ID 重新创建。
2. 原样保存真实 `externalThreadId`、当前 turn、创建中的临时标识及结果来源。临时创建标识与真实线程标识分开，不能用标题或 cwd 猜测外部会话身份。
3. 继续和修改固定发往原绑定。用户从另一聊天入口调整同一工作时，不新建一份外部线程。一个内部工作需要多个外部会话时保存多条明确关联。
4. 将相关 SSE 事件先保存到现有持久事件/通知记录，再用稳定消息 ID 投递负责的工作对话；只有入箱完成才确认投递。重复事件不重复启动同一执行或重复通知。
5. 进度事件可以保存和合并；完成、失败、待输入或影响当前委托的重要变化唤醒工作对话，由它判断下一步。普通心跳与无变化状态不反复调用模型或发群消息。
6. 事件游标缺口或断线后读取已知工作快照，补齐可获得的状态；缺失过程仍标为缺失。重启恢复订阅和待通知，不重新提交旧 prompt。
7. 工作对话整理结果，并根据来源关系向适当聊天通知。发送成功与用户可见、收到回执与实际完成分别记录；待通知重启后继续，重复结果保持同一去重 ID。
8. 查询到旧回合 completed 或 idle 不能当成本次续发工作完成。保留续发前后的 turn 关系；未知状态、不可用连接和空历史不改写成成功。
9. 已有 workspace 任务 JSON、请求结果文件与 `routines_create` 跟进记录在切换时归并到 S3。完成归并后移除被替代的每任务轮询职责和第二份工作状态维护路径；请求文件中的原操作键和有效结果作为来源保留。
10. 关闭 Web、手机或浏览器不停止 Bot 及后端工作。用户明确暂停/停止仍有效；桌面连接器断开只影响关联工作的可见性与可操作性，不默认认为 Codex 已经停止。

**完成行为**：用户交代后可以离开客户端；工作事件会回到实际负责的工作对话，必要时自动通知相关聊天。Bot 上下文重组、Web 关闭、连接器重连都不会生成第二份相同委托。

### 4.6 第六步：一次性转换与正式切换

**代码候选**：`scripts/installation/install.mjs`、`scripts/installation/current-version.mjs`、`scripts/installation/cli.mjs`、`scripts/build/build.mjs`；数据转换只作为本次升级的临时实现，结束后移除。同步涉及 `bot` 配置、相关能力工具与角色/Skill 文本。

实施顺序：

1. 完成新代码及必要配置变更，保留当前共享工作区中与本任务无关的增量。各步骤不另外部署临时服务。
2. 按既有正式安装流程正常停止需要更新的写入方，保留用户此前的运行/停止意图。持有实际外部工作的 Codex 桌面不因 Relay 升级被默认关闭。
3. 在原正式数据根中一次性转换旧 Bot 会话、任务、总结来源和工作关联。原始消息 ID、作者、时间、附件及来源继续可查；新的关联保留必要的 `legacySource` 信息。
4. 旧消息触发任务只转换为其真实的历史执行记录，不把每条旧消息制造成新的长期 work。能依据已存外部 ID、来源消息和工作记录确定的才建立 S3 关联。
5. 将旧压缩检查点作为已有历史材料保留；新运行不再按旧压缩链自动续写。初始 S2 在需要恢复相应对话时由维护侧按可获得的原始材料建立，并明确已覆盖范围。
6. 旧在途执行转为中断或结果未知记录；登记原操作 ID、外部线程和待核对状态。不能在迁移期间调用模型重做任务、复制在途 outbox 动作或重新发送创建请求。
7. 对有明确母体关系的旧任务分身，保存其有效历史、产物、知识增量和外部工作来源，归入对应 Bot 的内部对话/工作关系。保留旧身份的来源信息，不复制凭据，不合并普通独立 Bot。无法确定归属的记录保留为待明确的历史/工作关联，不能因清理入口而丢弃。
8. 已有有效外部绑定保留原身份。旧 app-server 历史可继续查询已有记录；实际能否续接按现存能力明确表达，不启动旧服务、不自动将旧工作迁到 Desktop 再做一遍。
9. 一次转换完成后，运行只识别新格式；移除转换代码、旧分身创建/交付/合并/回收业务入口及相关过时配置。普通独立 Bot 的创建、启停和自有积累能力继续保留。
10. 更新全部运行引用：Bot 内核、内部对话类型、上下文预算、工具路由、角色提示词、Skill、连接器与当前能力配置。`current-version.mjs` 目前只保留旧 compaction limits 的过滤逻辑须同步替换，否则安装会丢掉新配置。
11. 按当前正式安装流程选择新发行并恢复原运行意图。用户入口、正式数据根和已知连接器地址保持；不保留可运行的旧分身链、旧摘要链或旧版配置回退分支。
12. 清理被替代的发行、能力版本、配置和构建中间目录。清理前按实际路径和业务归属保留有效用户数据与被引用材料，结束后不留下备份或回退副本。

**现有清理逻辑的必要修正**：当前 `scripts/installation/current-version.mjs` 包含对数据根 `archives` 等目录的整体清理。3+3 转换必须先处理其中有效分身交付与仍被引用的业务材料，并缩小清理对象，不能把业务归档等同于旧发行物。历史记录保留在新归属后，旧失效业务入口才可移除。此项只处理本次转换涉及的有效记录，不扩展为全盘扫描或额外完整性工程。

**完成行为**：正式环境只运行新机制，已有聊天、工作和产物仍可继续引用；停止意图、未确认外部操作和待通知没有被升级吞掉。不存在为了兼容旧分身或旧自动压缩而长期保留的第二套执行路径。

## 5. 外部 Codex 的真实能力边界

本表依据当前仓内连接器源码；实施时使用其实际返回的能力和错误。3+3 不要求修改 Codex 私有数据库，也不把 Relay 内部上下文组装套用到外部 Codex 的模型历史上。

| 需求 | 当前接口与限制 | 实施口径 |
| --- | --- | --- |
| 查找项目和已有会话 | `GET /v1/projects`、`GET /v1/threads`；列表有近期数量范围 | 按实际项目 ID 和明确选择绑定，不把列表当作全部历史 |
| 创建工作 | `POST /v1/threads`；当前校验支持既有项目的 local 或明确 projectless，未开放 worktree 创建 | 在目标项目内创建，保存真实回包；不假造目录或新增工作树 |
| 继续或修改 | `POST /v1/threads/{id}/messages` 返回受理结果 | 不将 202 当作已采用或完成，也不冒充原生 `turn/steer` |
| 状态与结果 | `/state`、`/messages` 与会话读取；历史返回摘要且可能截断 | 保留可见范围、缺口和来源；不声称已读取完整外部模型轨迹 |
| 中断 | `/interrupt` 需要当前 `expectedTurnId`，实际能力依赖连接器协议 | 先读取当前状态，只停止对应轮；受理不等于所有外部动作已停止 |
| 未知写请求 | `GET /v1/operations/{key}` | 用原操作键查明，不能换键重发以制造第二份工作 |
| 事件恢复 | `/v1/events` 支持线程/主机范围与游标；有保留范围和缺口 | 订阅已绑定工作，持久入箱；缺口以快照补齐已知状态 |
| 出站 webhook | 当前队列有界、内存持有，重启可丢未完成通知 | 可作为提示；主链沿用已有 SSE/只读恢复，不把 webhook 当持久队列，不为本方案新增签名工程 |
| 归档 | archive/unarchive 与中断是不同操作 | 逻辑会话封存不触发外部删除或取消 |
| 桌面审批与登录 | 当前连接器没有审批回答、登录接管接口 | 保留待用户状态并指向真实桌面操作；不让同伴意见变成批准 |
| 多后端切换 | 当前首版新工作固定 Desktop | 不自动启用 app-server，不迁移活动会话，不为未知结果切换后端重做 |

当前连接器的鉴权、来源校验和受控工具名单继续保留。无需为 3+3 新建 RBAC、企业权限中心或审批平台，也不能以“简化”为由拆掉已有公网入口认证和工具允许范围。
