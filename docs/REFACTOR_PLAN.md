## 1. 用户决定与交付目标

本方案汇总本轮讨论，并替代旧基础框架迁移方案中与本方案冲突的目录、运行单元及兼容策略。

## 2. Bot 的定义与职责边界

一个 Bot 是以独立 Pi Agent 为决策核心，拥有自己的身份、任务、上下文与持久化状态，能收发消息、调用配置的工具和使用 Skill 的独立工作单元。

所有角色使用同一套 Bot 程序。工程、质量、组件、入口、聊天室组织、管理、记忆整理等角色通过配置和能力组合形成。模型供应商可以共用；各 Bot 的 Agent、上下文、运行状态和可写数据独立。

### 2.1 Bot 本体必须具备

| 组成 | 责任 |
| --- | --- |
| 身份与配置 | 加载稳定 Bot ID、角色、模型、工具权限、工作目录和数据目录 |
| Pi Agent | 理解任务、模型调用、工具循环、观察结果、继续执行、中断和结束本轮 |
| 自身生命周期 | 初始化、恢复、待机、运行、等待、正常关闭；报告自身状态 |
| 消息机制 | 收发 bot2bot/bot2group 消息，消息标识、来源、目标、回复关联、回执、去重 |
| 自身待办 | 入箱、排队、执行、等待、取消、失败、完成和交付状态 |
| 上下文 | 按私聊、群聊、任务区分会话；按需加载历史、记忆和 Skill；压缩模型视图 |
| 持久化 | 保存会话、工作状态、工具事实、长期记忆和产物引用 |
| 能力接入 | 通用工具注册、API/MCP 连接、Skill 加载、执行结果与错误处理 |
| 证据与运行限制 | 请求/任务/工具关联、完整输出引用、用量、超时、取消和配置的访问边界 |

启动一个 Bot 必须创建自身 Pi 引擎。模型凭据缺失时明确报告未配置/不可执行，不能悄悄退化成一个仅转发消息的假 Bot。模型不必持续生成；待机只等待事件。

第一版同一上下文串行执行，接收入口和状态查询不被长工具阻塞。长任务可以返回后端任务编号，由完成事件继续推进；需要独立并行思考时由外部创建另一个 Bot。

### 2.2 交给外部的能力

| 外部责任 | 承担者 |
| --- | --- |
| 创建身份、部署、启动、停止、监控、崩溃后拉起 | 生命周期脚本/API，必要时由管理 Bot 编排 |
| 复制状态、选择继承内容、分身关系、回收 | bot-management 能力及管理角色 |
| 跨 Bot 记忆汇总、冲突分析、合并 | memory-management 能力及记忆角色 |
| 文件、命令、Git、Unity、应用操作 | 各专业能力的 API/MCP/脚本 |
| Codex 长任务 | codex 能力，保存后端会话、任务和 cwd 关联 |
| 房间、成员、公共聊天记录、消息分发 | chatroom 确定性能力 |
| 共享知识、关系和来源 | knowledge 能力 |
| 定时唤醒、联系人发现、系统状态汇总 | 外部能力；只把需要判断的事件交给 Bot |
| 网页、附件下载、PWA、用户访问协议 | web 子项目 |

聊天室 Bot 负责理解讨论目标、组织参与者和整理结论；聊天室服务负责确定性的房间和消息操作。管理 Bot 负责判断和编排；管理 API/脚本实际执行进程与数据操作。二者不能混称。

### 2.3 工具、MCP/API、Skill 与其他 Bot

- 脚本/组件提供可执行操作；API/MCP 提供明确的参数、结果和连接方式。
- Skill 提供使用方法、流程、约束和检查步骤，不承担守护进程、数据库或消息传输。
- 其他 Bot 是有自己 Pi Agent 的协作者，不是隐藏在一个全局 Supervisor 下的函数。
- 工具接入不能只支持旧内置函数。至少验证一个配置式 API 工具和一个真正可互操作的 MCP 工具；不得把自定义 HTTP 协议仅改名为 MCP。
- 能力按业务职责纵向组织，一个目录可含实现、脚本和协议适配；不为每个工具强制启动独立服务。
- 角色可以调用外部复制/合并工具，但这些实现不得成为 `bot/` 的静态业务依赖。

### 3.1 独立 package 的实质

`bot/` 必须有依赖声明、公开 exports、CLI 入口、包内测试和最小配置示例。根工程通过 npm workspaces 组织实际 package；roles 和 skills 是资源，不必各自成为 npm 包。

核心不能静态引用 `web/`、专业 `capabilities/`、根工程配置加载器或旧 Relay 数据结构。专业能力经配置式工具接口连接，角色资料由配置装载。拆分应包括实际依赖整理，不允许仅增加 package.json 后仍跨目录引用旧业务源码。

模型循环、会话修复、压缩和 Skill 加载收进核心。Pi 固定当前实际 1.3.0 依赖，不把目录重构和 Pi 升级混在一起；上游许可证与来源记录保留在新的合法归属。

## 4. 消息、任务、接口与模型执行

### 4.1 通用消息

消息至少含 `id/from/to/kind/content`，按需含 `sessionId/taskId/replyTo/correlationId`。消息可以来自用户入口、同伴、群服务、定时器和工具完成事件。来源身份由传输认证确定，不能仅相信正文中的 from。

接收成功、任务开始、处理中、等待、最终结果分别记录。消息重复投递读取已有收据，不重复执行外部副作用。发送失败与结果未知分开；未知执行不能盲目重试。

Bot 自身入口提供健康/能力、接收消息、查询任务/结果、取消、事件订阅和正常关闭。内部 API 限定回环或配置的可信连接并认证。普通状态查询不调用模型。

对外公开 `startBot(config, dependencies)` 等明确接口及 CLI（最终名称记录在 ARCHITECTURE）；不要求外部调用者提供 createApp 或自己实现 Agent 循环。

### 4.2 工具契约

工具定义包含名字、说明、参数 schema、执行函数/远程映射和可观测结果。SDK 工具名称使用其实际允许字符；协议 operation 可独立使用带点号的名称。

运行记录关联 Bot、请求、任务、session、tool-call、开始结束、状态、错误、退出码、完整输出与产物。模型可得到裁剪结果，但完整结果可查询下载。错误不能包装为普通成功文本。

Codex 等长任务返回后端任务标识，提供查询、取消、结果读取和完成通知。停止 Bot 不代表后台任务已停止；状态和责任需记录。

Codex 向同伴查询项目事实与请求用户选择/授权必须分开：前者可交给相关 Bot，后者保留给用户，不用模型自动代替用户作答。

Codex 持有某工作区写锁期间的咨询不得再次等待同锁写工具；使用只读咨询或显式释放/移交后重新核验的边界，避免循环等待。

### 4.3 上下文与群唤醒

私聊、群聊和专项任务分别保存上下文。按目标读取必要经验，原始历史可检索；压缩只改变模型视图，不覆写原始记录。群消息依据职责、提及、订阅和任务关联唤醒；去重并识别自身消息回流，允许保持沉默，避免无限互相回复。

Bot-to-Bot 已知地址通信不依赖网页进程。群服务负责公共历史，Bot 只拥有自身阅读位置、任务和上下文。

## 5. 打包、安装与运行结构

完整应用发行物与单独 Bot npm 包都要可验证：前者部署整套系统，后者可在仓库外安装并启动一个 Bot。

本机目标安装根使用 `D:/Relay-Bot-app`，持续数据沿用 `D:/Relay-Bot-data`。部署位置均可显式配置；运行不依赖源码工作目录。

```text
D:/Relay-Bot-app/
  Start.ps1 / Stop.ps1
  current.json
  releases/<release-id>/
    release-manifest.json
    runtime/node.exe
    node_modules/
    bot/
    web/
    capabilities/
    roles/
    skills/
    scripts/installation/
```

- 一个版本的程序可供多个独立 Bot 进程使用。进程固定具体 release-id，不在执行途中随 current 指向混用新旧模块。
- 发行包包含全部生产依赖与运行必需资源，不能含指向开发仓库的 workspace 链接。
- 不打包真实 .env、密钥、运行数据库、Bot 记忆、用户项目、测试现场数据或开发缓存。
- 模型凭据通过部署配置/环境或凭据引用取得，不要求生产环境读取开发仓库 .env。
- 可重复构建并生成文件清单、内容哈希、运行时和数据 schema 信息。
- 本轮按用户要求不保留旧版本作为回退副本。切换成功后删除被替代版本；只保留当前版本和仍被实际进程引用的版本，后者结束后回收。
- 保留用户原访问地址、HTTP/SSE 与 PWA 使用体验。Web 是普通服务，入口/聊天室等角色 Bot 均以统一 Pi Agent 运行。
- 接入已有 StartupHub，不新增另一套登录触发器，不变更其他启动项。Windows 后台启动隐藏窗口，PowerShell 5.1 文件编码经过实际验证。

## 6. 每个 Bot 的数据与共享数据

```text
D:/Relay-Bot-data/
  config/                         部署配置、角色覆盖和凭据引用
  bots/<bot-id>/
    config.json                   稳定身份、角色、模型、工具、工作位置
    state.sqlite                  入箱/出箱、任务、会话、工具事实、关联
    memory/                       可编辑长期记忆及来源版本
    resources/                    自定义 Skill、提示词等
    artifacts/                    完整输出、截图、交付产物
    workspace/                    自有工作文件
    logs/                         运行日志
    cache/                        可重建缓存
    run/                          当前进程身份与地址
    tmp/<run-id>/                 本次执行临时文件
  capabilities/
    chatroom/                     房间、成员、公共消息与附件
    knowledge/                    共享知识与来源
    codex/                        后端会话/任务关联及执行证据
    bot-management/               启动意图、派生关系、交付/回收状态
    memory-management/            合并提案、冲突和处理收据
  web/                            展示同步游标等界面自有状态
  archives/                       已结束 Bot 的必要业务归档
  verification/                   本次及后续验收报告和必要证据
```

不创建 backups 目录或新的旧实现快照。业务归档不是备份：它保存已结束 Bot 的工作事实，是正常产品数据。

### 6.1 归属与一致性

第一版一个 Bot 身份对应一套目录和一个活动进程。重启沿用身份与目录，boot/run 标识变化；复制创建新 Bot ID。外部管理元数据记录母体关系，Bot 内核不依赖该关系执行。

SQLite 保存结构化事实与索引，长期记忆正文可用 Markdown，长输出/附件用文件并保存关联与校验。必须明确哪份内容是权威原文，索引可重建，不能维护两份无同步约束的正文。

公共群历史只由 chatroom 能力持有，共享知识只由 knowledge 能力持有。Bot 自己保存上下文和引用，不读取所有 Bot 的私有状态库来拼提示词。

活跃数据通过正常存储接口/事务/版本检查修改；离线修改确保独占。核心不增加分身专用导出/合并协议。

### 6.2 临时数据与回收

| 内容 | 策略 |
| --- | --- |
| 身份、消息、任务、会话、记忆 | 持久保存，停止后保留/归档 |
| artifacts | 保留引用有效性，不按临时文件规则清理 |
| workspace | 未交付修改保留；外部项目仅记录引用，不能随 Bot 回收删除 |
| logs | 配置容量/保留期轮转；关键事实另有结构化记录 |
| cache | 仅删除可重建且不在使用的内容 |
| run | 新启动重建，不复制给分身；旧 PID 文件不是杀进程依据 |
| tmp | 归属 run 已结束、成果已落盘且工具/后台任务不再使用后清理 |

临时 Bot 同样有正式持久目录。崩溃遗留临时文件先核对任务，不按年龄直接删除未知执行证据。清理只作用于明确受管目录，解析路径与 junction/symlink 后检查边界。

## 7. 外部分身管理与记忆合并

### 7.1 创建与执行

1. 用户或 Bot 提交任务、母体标识、继承范围、工具边界和结果接收方。
2. bot-management 通过正常停止后的复制或存储层一致性读取，取得逻辑状态。这里是创建子任务的数据初始化，不额外保存旧实现备份。
3. 分配新身份和数据目录，选择角色、上下文、专业记忆、资源与新任务。
4. 不复制 PID、连接、锁、运行密钥、待重放出箱或正在执行的外部副作用；未确认操作作为只读关联/待核实事实保留。
5. 使用标准 Bot CLI 启动；分身和长期 Bot 运行完全相同的程序。
6. 管理方记录派生来源、基准版本、创建请求收据、工作区和交付目标，重复请求返回既有结果。

### 7.2 成果与合并

分身正常保存结果、证据与新增经验。管理方收集相对基准的新增/修正信息，而非用分身全量状态覆盖母体。

- 确定性去重、版本检查、记录追加由普通工具执行。
- 经验筛选和冲突判断由母体或受委托的记忆 Bot 使用 Pi Agent 完成。
- 最终写入经普通记忆接口；冲突保留双方来源和适用条件。
- 代码或外部项目文件的合并独立于记忆合并，不能用“记忆已合并”表示代码已合入。
- 主 Bot 离线时成果进入可独立访问的持久交付记录，允许分身退出；保留“已交付、待合并”状态。
- 归档或删除前检查附件引用，必要时转移归属并更新引用。

### 7.3 管理职责

管理 Bot 是有生命周期工具的普通 Pi Bot，可被直接调用。确定性启动、复制、收据和回收无需每次先经过模型。它不是其他 Bot 通信和决策的全局主控。该能力必须有真实流程验收，不能只交付一份 Skill 或接口占位。

## 8. 数据迁移、旧目录清除与现场切换

### 8.1 迁移来源

当前实际来源包括 `D:/Relay-Bot-data/legacy`、旧 instances、旧 Bot workspace/memory，以及仓库 `.relay` 中仍有唯一价值的原始记录/产物。实施前查询当前进程与状态，不沿用历史 PID 和计数。

迁移逐项分配数据归属：Bot 私有会话和工具事实入对应 Bot；群和消息入 chatroom；共享知识入 knowledge；Codex 入 codex；派生/启动元数据入 bot-management；历史验收证据入 verification。迁移保留原始 ID、时间、作者、任务关系和附件内容；已确认记录不改写为新模型输出。

旧 UI 与 worker 中同 ID 的 jobs/agentRuns/toolRuns 以执行 worker 的完整记录为权威，UI 记录仅作展示来源；缺少 worker 原文时保留来源说明，不能用较新的 UI 投影覆盖完整执行事实。导入前比较冲突，记录最终选择。

### 8.2 不做备份条件下的顺序

1. 读取当前源码/历史数据清单，仅记录数量、标识和必要哈希，不另存整份旧源码或旧数据库。
2. 用隔离数据完成新程序验证，不让新旧进程同时消费真实消息。
3. 核对真实任务，正常停止原写入方，等待数据库/身份锁释放。
4. 将业务数据迁入最终归属，验证行级关联、文件哈希、重复导入和查询结果。
5. 只有新归属验证通过才清除旧来源；若验证失败，修正新迁移，不伪称完成或提前删除唯一数据。
6. 从新发行物启动，核对原 URL、原历史、真实模型/工具与后台任务边界。
7. 更新 StartupHub 到新入口，完成实际停启和状态读回。
8. 清除全部受管旧运行链、源码目录、旧发行物和替代副本，留下清理清单及校验结果。

迁移过程中短暂同时存在来源与目标用于校验，不把来源改名成永久兼容/回退目录。对外部用户项目和无关目录没有删除授权。

### 8.3 最终清理范围

源码根不再存在旧 `src/`、`bots/`、`adapters/`、`templates/`、`public/`、`test/`、根 `third_party/` 或 `scripts/foundation/`。实际需要的实现、测试和许可证先归入新路径。

旧 `ui-entry`/`legacy-compatible` 应用、旧 worker pool、旧 CLI、旧绝对路径、过时文档和旧构建脚本引用不得继续参与运行。旧 `.relay` 唯一业务记录迁走后删除。清除已核实属于本项目的旧 `dist/current*`、delivery-check、旧 migration/backup/rollback 候选；不删 Git 历史、当前生产数据、有效业务归档或其他工程。

仅把字符串改名或把整个旧 SocialRuntime 搬进新目录，不满足职责拆分。保留前端协议属于产品兼容，不是保留第二套旧后端。

## 9. Git 与协作规则

- 在当前 main、当前共享工作区实施，不另建分支，不重写已有历史。
- 将现有未提交功能作为当前基线，移动时保留实际内容；不依赖 Git HEAD 恢复文件。
- 分工按新目录和明确文件所有权，根 package/lock、入口、集成和现场切换由主控统一处理。
- 使用精确路径暂存，检查移动/删除、秘密信息、运行数据和构建产物，避免无审查 git add -A。
- 最终提交包含新源码、方案、必要文档、测试和旧源码删除；不提交密钥、用户记忆、数据库、node_modules、安装包或现场附件。
- 推送 origin/main，比较本地 HEAD 与远程分支 SHA，报告提交号及实际推送结果。
- 如远程前进，先检查变化并进行非破坏性整合；不强推覆盖他人工作。
