# Summon Bot 单包安装与欢迎引导改造

## 交付范围

Windows x64 和 Apple Silicon Mac 分别发行一个 Summon Bot 桌面安装包。每个包包含对应平台的 Node 运行时、完整服务端和生产依赖、Codex 桌面 API 连接器、Web 页面及 Electron 外壳。复用现有服务端构建、安装、启停和应用签名身份，按同一源码提交生成桌面包。安装一次即可在本机创建工作区，也可以把该桌面应用作为现有工作区的客户端。

Web、Windows/macOS 桌面、iOS、Android 继续组成四类终端。Web 与 Electron 使用所连接实例提供的同一套页面，iOS 与 Android 使用现有原生界面和 API。后端部署机负责运行 Bot、存储数据和接入本机工具。远程访问提供现有 Cloudflare Tunnel 和新增 Tailscale Serve 两种选择。本机工作区安装时即可使用回环入口，配置远程访问是可跳过的后续步骤。

现有正式实例继续使用 `D:/Relay-Bot-app`、`D:/Relay-Bot-data`、`http://127.0.0.1:8787` 和 `https://bot.lin0.org`。适配通用安装包时，其他用户的数据目录从其本机应用设置或明确选择的路径取得。安装产物携带程序和默认配置，每台机器独立生成令牌并保存自己的配置、会话、记忆、工作和文件。

## 安装包与运行模式

| 操作 | 应用行为 |
| --- | --- |
| 首次打开 | 默认打开纸箱并准备本机工作区。发现桌面安装记录里的已有工作区时，在纸箱页询问复用还是新建。新建使用新的数据目录，停止上一个由此安装管理的工作区服务。远程工作区仍可从切换工作区入口连接。 |
| 在本机使用 | 由桌面主进程调用包内 Node 和现有安装、启动入口，初始化选定数据目录。纸箱撕条显示运行组件复制和服务启动进度，就绪后开箱并进入工作区。桌面创建的工作区默认使用 `http://127.0.0.1:8787`，端口被占用时自动绑定并保存空闲的回环端口。登记远程入口后，本机端口随转发配置固定。桌面通过本机受信通道完成首次 Web 登录，再进入模型引导。 |
| 连接已有工作区 | 对话收集地址，通过隐藏输入或该实例登录页提交访问令牌。已配置的工作区直接进入使用。远程模式跳过内置后端、连接器和隧道的初始化与启动。 |
| 更换连接 | 从设置、应用菜单及连接失败页均能回到欢迎对话。保存用户成功选择的地址。只停止由当前桌面安装管理、且本次切换明确要停用的服务，保留本机数据；外部管理的服务按其原有控制入口运行。 |
| 关闭窗口 | 本机服务和窗口生命周期分开。用户可以从桌面明确停止工作区。供手机或其他电脑访问时，关闭窗口后仍可继续运行本机服务。 |
| 安装升级 | 停止正在使用旧代码的受管进程，切换当前发行，沿用数据目录、应用身份及访问令牌。迁移当前有效配置后清理被替代的运行文件。使用远程工作区时，更新客户端不启动本机后端。 |

桌面程序启动前明确连接模式，发布的通用包在未选地址时直接显示欢迎对话。连接地址属于运行配置，客户端发行来源属于发布配置。保持设备本机发行物优先、GitHub Releases 回退的更新路径。桌面 IPC 和导航限制跟随用户选定的实例，保存地址、启动和停用本机服务由受信的本地入口控制。远程网页通过当前实例的登录和 API 使用工作区。安装包、命令输出和调试记录中只出现脱敏状态。

打包复用 `scripts/build/build.mjs`、`scripts/installation/` 和 `desktop/build.mjs`。内置后端和 Node 放入独立运行资源，供操作系统启动。Node 及生产依赖跟随目标平台和架构，业务数据保存在可写目录。macOS 发行继续使用现有 Developer ID 和公证流程，内置可执行文件一并纳入。GitHub Actions 从同一提交构建发布各平台，Windows 本机包沿用本机发行目录。制作和独立验证期间先提供候选产物，正式环境部署与正式发布遵守现有定稿流程。

## 欢迎 Bot

在设置中保留可再次进入的「新手引导」。已完成配置的工作区打开时直接进入工作台。新装未配置、用户主动重开引导或当前步骤等待授权时恢复对应进度。

1. **本地脚本对话。** 欢迎 Bot 用脚本消息完成首次选择和连接。安装启动本机服务后，引导用户选 API 提供商、协议、API 地址及模型，再用隐藏输入保存 Key。保留现有明确选择后的订阅授权、本机登录导入和自定义兼容 API。脚本阶段可离线展示，模型连接由服务端保存，脚本消息和秘密字段与真实聊天记录分开。
2. **在私聊中配置。** 聊天模型保存后，主 Bot 的引导消息直接写入现有私聊。每个步骤只追加一条实际要问的问题，当前选项附在对应消息里。刷新、双击和重启沿用已保存的步骤及消息。
3. **先配置工作引擎。** 首条消息提供 Codex、Grok 和 Claude Code 三个选项。三个引擎采用部署机上已登录的命令行工具。选择 Codex 后，在消息中点击「同意并接入 Codex」即可使用本机的 ChatGPT 订阅登录和 Codex 配置。工作会话由程序创建并保存，后续步骤继续同一个工作会话。选择及授权独立于聊天模型，新委托按配置在现有工作队列中执行。
4. **再配置远程访问。** 选定工作引擎后，主 Bot 询问是否从其他设备访问。用户可以选择只在本机使用，或按私网和公网需要配置 Tailscale Serve 或 Cloudflare Tunnel。入口和错误提示出现在对应的引导消息中，密钥留在受控输入里。

Web 与原生端共用后端引导状态和现有模型接口。优先整理网页行为，再同步 iOS 和 Android 的对话式连接、进度和可跳过步骤。已保存的手机连接继续可用，新装优先填写用户自己的地址。iOS 切换服务时处理旧服务离线或令牌失效，避免旧推送注销阻断新工作区连接。系统 VPN、Codex 及供应商授权仍使用各自的用户确认界面。

## Codex 工作接入

新手引导通过官方 Codex CLI 接入本机订阅。确认时运行 `codex login status` 读取登录状态，工作执行采用 `codex exec --json`，续接采用明确会话 ID 的 `codex exec resume`。会话 ID 在创建时自动记录到对应工作。登录、模型及权限使用本机 Codex 配置，凭据由 Codex 自己管理。用户只需确认接入。

已有桌面对话绑定的工作继续由下述桌面 API 连接器处理。新手引导与模型设置的 Codex 接入使用命令行执行器。

### 已绑定的桌面工作

连接器随服务端打包，供部署机上的工作执行链使用。保留现有 HTTP/SSE、工作与 Codex 线程及操作 ID 的绑定、用户明确接入、桌面权限继承和本机回环端点。导入聊天订阅和启用 WORK 执行器分别记录。可在未接入时从引导看到准备项，明确选择后才启动或连接本机适配层、读取额度及使用桌面聊天。

Windows 复用当前 IPC、发现及权限实现。Mac 以实际安装的 Codex 桌面为依据确认工具端点、会话 IPC 和权限握手。现有 `FramedPipe` 可接收两平台的套接字地址，`toolsPipe`、`ipcPipe` 支持显式配置。使运行目录和启动入口跟随当前安装和数据根，优先复用共同协议。目标端点不存在、权限握手失败或平台适配尚缺条件时，返回明确状态并让用户继续使用 Pi 工作。Mac 连接结果按现场证据说明。

相关入口为 `connectors/codex-desktop-api/src/`、`capabilities/codex/desktop.mjs` 和 `capabilities/models/service.mjs`。

## 两种远程入口

同一实例可以保留本机回环、已配置的 Cloudflare 地址和已配置的 Tailscale 地址。扩展现有 `publicOrigin` 的单地址模型时，把当前值一次性迁入生效的远程配置。Web 登录、Cookie 与跨源检查匹配用户访问的已登记 HTTPS 地址，匹配经过规范化的协议、Host 和端口。继续使用现有工作区令牌，代理保持原始 Host 并实时转发 `/api/stream`。入口仅转发 Web，网关、控制端和 Codex 连接器都在本机受控运行。

| 入口 | 对话可做的配置 | 外部条件 |
| --- | --- | --- |
| Cloudflare Tunnel | 复用已配置的公开 HTTPS 主机名和 `cloudflared`，确认本机目标 Web 端口。对于用户选择由 Summon 管理的连接器，收集已建隧道的凭据，使用私有令牌文件或官方支持的私有配置启动，查询连接状态。 | 用户拥有或获准管理域名和隧道，已发布主机名，部署机的 `cloudflared` 可以连接 Cloudflare。 |
| Tailscale Serve | 检测部署机的官方 Tailscale 客户端、登录和 Serve 状态，用户确认后为本机 Web 建立一条私网 HTTPS 转发，把分配的 `https://…ts.net` 地址加入实例配置并提供给用户。保留已有 Serve 映射。 | 用户完成登录与私网 HTTPS 授权，手机或另一台电脑加入该 tailnet 并有访问权限。 |

Tailscale 首版复用系统已安装的官方客户端及 Serve，缺失时提供官方安装和授权指引。桌面包包含接入引导和配置操作。保留现有 Cloudflare 正式配置的归属，新增远程设置由使用者操作自己获准管理的资源。对非本应用创建的外部隧道及 Serve 映射采用查询和复用。应用自行管理的转发以明确的目标、端口和归属记录精确启停。

本地网络变更经用户确认后由桌面本机控制层或安装后的本机 CLI 执行，提供查询、准备、应用和撤销该条配置的结果。反向代理也可能连到回环，不能仅以请求源地址判断控制权限。模型工具的操作范围绑定本次确认的配置动作。访问令牌、供应商 Key、隧道凭据和外部授权不进入普通消息、源码、工作日志或验收记录。

参考 [Cloudflare Tunnel 配置](https://developers.cloudflare.com/tunnel/get-started/) · [cloudflared 令牌文件](https://developers.cloudflare.com/tunnel/reference/run-parameters/#token-file) · [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) · [Serve CLI](https://tailscale.com/docs/reference/tailscale-cli/serve)。

## 程序化操作与验收

复用安装 CLI 的 `init/start/status/stop`、Web 访问认证、`/api/state`、`/api/model-settings/onboarding` 及其 `reply/start`、模型连接及执行器 API、聊天和 SSE。以实现后的正常入口为准记录具体命令、请求及返回状态。缺少桌面连接模式或本地接入的操作入口时，补随安装包交付的 CLI 或已鉴权的本机控制接口。程序化方式与界面使用相同的校验、状态、权限和执行逻辑。

程序应能读取已安装版本和模式，选定本机或远程，启停与查询本机服务，按步骤驱动引导，查询、确认及应用两种接入配置。输出结构化状态和明确退出码，凭据经隐式输入、文件或私有配置传入。验证使用实际安装后的程序、CLI、HTTP/SSE、进程和系统安装工具。可用 `adb` 或 `simctl` 做程序化安装和启动。全流程使用程序操作，排除电脑使用工具、截图点击及按键驱动。

候选产物从制作对话提供的同一版本取得。首次安装、升级与失败分支用按次释放的 Windows 和 macOS 验证主机或 CI runner，结束后停止受管进程并清理本次验证的安装。当前正式主机不另起并行验证服务、不替换生产数据、不改现有域名或私网设置。受控模型服务可以用于可重复的引导验证，须让真实的 Pi 请求、响应和工作记录走正式链路。实际第三方登录、域名或权限要用已授权资源，报告时区分受控替身、实际网络验证及缺条件的项目。

| 验收项目 | 程序化结果 |
| --- | --- |
| Windows / macOS 安装 | 实际安装或解包候选 EXE / DMG，使用包内 Node 启动本机工作区。Web、网关和欢迎引导可用。升级保留已有会话和私有配置，重启复用同一实例。 |
| 两种连接模式 | 本机选择生效并访问回环 Web。远程选择访问指定实例，本机后端、连接器和转发进程没有被启动。失败可改地址，切换只影响本应用拥有的进程和连接。 |
| 欢迎 Bot | 新实例可操作脚本对话并配置模型，模型不可用可返回更改。首条真实回复来自实际 Pi 路径，房间与进度在重启后续接，重复操作不生成重复会话。检查返回内容和聊天数据不包含输入秘密。 |
| Codex | 默认未接入，连接过程等待用户动作。接入后读取状态，实际端点可用时完成一次由当前权限约束的工作并收回结果。分别记录 Windows 和 Mac 的真实握手和工作状态。 |
| Cloudflare 与 Tailscale | 走程序化本机操作，覆盖外部组件缺失、未授权、已配置复用和授权成功路径。两个已登记 HTTPS 地址分别验证登录、API 和实时 SSE，额外 Origin 被拒绝。真实隧道或 tailnet 的验证按实际授权资源记录。 |
| 四端 | Web 与桌面连接同一工作区。iOS 和 Android 使用自定义地址和令牌并完成相同引导与状态读取。记录真实设备、模拟器或协议层各自覆盖的范围，旧端地址不可达时检查可重新连接。 |

验证对话把一轮所有可运行项执行完，再记录每项的候选版本、实际操作、结果与可复现问题，区分通过、失败和外部条件缺失。每次修复后基于新候选重新验证受影响路径及完整安装链。依据实际结果判断完成。

## 交接顺序

1. 新建 `gpt-6.1-sol`、`max` 制作对话，创建 Goal 承接本改造。由该对话负责代码、接入、构建、修复和后续验证调度。共享工作区已有独立改动，交付只包含本任务范围。
2. 制作对话完成实现并给出可供安装的候选产物后，新建 `gpt-6-astra`、`max` 验证对话。验证对话独立执行完整的程序化安装验收，将一轮结果和问题留在 Markdown，完成整轮后交回原制作对话。
3. 制作对话根据问题记录修复，准备新候选并交给验证对话复验，直到安装和功能验收没有未解决的问题。外部账号、凭据或设备条件缺失时列明具体项目及实际缺项。用户请求的安装验证按本节执行，仓库其他测试、哈希和额外验收约定继续遵守。
