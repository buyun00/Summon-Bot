# Summon Bot 运行链路改造制作文档

本文件是制作对话的实施依据。目标是在现有 Summon Bot 中完成普通接话、一次性提醒、Pi／Codex 工作发起与续接、结果回流及按需记忆维护。以根目录 AGENTS.md 和 docs/DEVELOPMENT.md 的当前约定为准。

## 1. 产品行为和程序边界

用户始终通过原来的私聊或群聊与 Bot 交流。房间是公开消息流，work 是持续任务，执行器会话保存这项工作的过程。三个对象各有自己的身份和生命周期。同一个 work 可以接收多轮用户要求。

快模型负责理解用户、按需查资料、选择证据、写交接说明和发出工具调用。程序按真实引用读取并保留原文，按已有绑定投递，记录执行回执和向用户发布结果。沿用现有 Bot 循环、工具注册、调度、能力服务和数据根。接话、读资料、设提醒和工作交接通过具体工具完成，跨回合等待复用现有的持久工作状态。

### 模型交接使用现有材料继续

模型侧接受自然语言和可用的结构化信息。交接说明、引用、摘要、受理文案和最终答复按实际可用内容处理。可选字段缺失、额外字段、文字格式不同或部分引用无效时，使用可读的原话和材料继续，必要时说明缺口。工具参数只保留执行该动作所需的最少信息，能从当前请求或已有绑定取得的字段由程序补齐。模型输出可以提供参考信息，程序不以严格格式、固定措辞、语义评分或额外审查作为业务交接的前置条件。

每次交接保留用户原话、已取得的材料和已有进展。引用逐项读取，单条找不到或格式读不懂就略过该条，缺几条照样交付；有必要时随手带一句缺项说明。查资料、发起或续跑、等待和唤醒、结果回流、提醒、总结和记忆都按这个规则处理。一个步骤有问题，只影响依赖它的动作；其他步骤继续，已保存的工作、执行结果和通知记录照常保留。

工具收到不完整的参数时，先用当前请求、已知绑定和可用默认值补齐。仍有缺口时，前一个模型还在运行，就用普通工具回执告诉它哪里没拿到，让它补查、改参数或继续；已经交给后一个模型，就把原话、可用材料和缺口一起给后一个模型，让它按需处理。部分结果、纯文本和空的可选内容都能流转。复用现有回执和工作状态，避免另加审查模型、整轮回滚或反复自动重试。

权限、实际执行目标、事件归属和幂等以程序已有记录为准。线程、回合、操作 ID 和修订号由程序取得，模型用普通文字说明下一步或做了什么。确实无法确定目标、时间或满足用户明确要求的前置条件时，仅把那个动作的真实状态交给负责模型；保留其他工作的进度，等模型补齐后接着做。

| 用户请求 | 制作完成后的行为 |
| --- | --- |
| 普通聊天 | 快模型读取已发布的对话和本次原话，产生公开回复，程序追加到当前房间。 |
| 「一小时后提醒我喝水」 | 快模型调用一次性提醒工具。保存成功后显示受理；到点由程序按原房间发送正文。 |
| 「先查项目群里定的排序规则，再让 Codex 改网页列表」 | 快模型通过只读工具查群并选择原文引用，创建工作并发起 Codex 执行。Codex 在自己的线程里完成工作并写结果；程序沿原请求回发。 |
| 「看一下 B，再继续 A」 | 快模型按需读 B 的已保存原文，向 A 交付新要求和相关材料。若用户要求 B 作出新判断，则在 B 原会话询问，实际结果到达后沿指定的依赖交付 A。 |
| 回复 A 的结果提出新要求 | 通过来源消息和 work 关联找到 A，续用 A 的原会话或外部绑定。普通主线消息里含糊提到 A 时，由接话模型判断归属。 |

## 2. 房间入口和快速上下文

### 当前代码

- capabilities/chatroom/service.mjs 的 post、knownOwner、inputFor 和 deliver 保存房间消息、识别回复关系、生成投递包并发布回复。当前投递使用来源消息 ID 和房间游标。
- bot/src/storage/store.mjs 的 acceptMessage 按真实来源和消息 ID 去重，保存原始输入和任务。
- bot/src/agent/engine.mjs 的 buildMessages 当前会在旧历史前面插入动态状态与组装内容。该文件还在接话启动时尝试维护组装。bot/src/agent/activity.mjs 的活动描述会按条件另外调用模型。

### 实施

1. 使用房间中已经提交的公开记录构造快模型视图。沿用稳定的消息 ID 和顺序，保留作者、正文、引用、附件关系以及实际需要的角色边界。复用当前投递的消息位置和原文读取。需要补齐游标缺口时按原记录读取，再生成该轮输入。房间中其他 Bot 的公开消息也带真实作者，避免把引用或同伴陈述当作当前用户要求。
2. 在一次上下文代次内固定提示词、工具定义、工具顺序和历史起点。普通快模型首请求使用「固定提示词和工具定义＋公开历史＋本轮原话」。工作实时状态、执行器连接状态和临时查到的资料由工具按需取得，进入本轮尾部。正常接话期间不重新生成已送出的历史文字。超出窗口、关键配置或访问范围变化时，在安全消息边界开启新代次。
3. 快模型的每轮处理可以包含多次模型／工具往返。临时工具输入和结果保存到 S1 并标明归属；下一轮快模型的公开视图从真实发布的房间消息生成。A 发布的结果即使没有唤醒快模型，也会在下一次从房间读取时进入公开视图。
4. 让快模型选用可用的快速模型配置，将接话模型选择和 work 的执行器绑定分开。继续使用已有连接配置与授权。Pi work 可用明确选择的模型；已有 work 续跑沿既定绑定，配置缺省时沿用当前有效配置。无需额外常驻的分类对话。
5. 将普通接话和移交进度改用实际的模型、读取、受理、启动、等待和结果事件。去除快入口上单独为了活动文案发出的模型调用。普通聊天在模型可直接答复时走一次正常接话。

### 缓存边界示例

设 P 为固定指令、工具定义和此前公开消息，aaa 是用户新消息，bbb 是受理答复，ccc 是 A 后续发布的结果。

~~~text
首个快速请求        P | aaa
本轮需要查资料时    P | aaa | 本轮工具调用及返回
主线已发布内容      P | aaa | bbb | ccc
下一轮首请求        P | aaa | bbb | ccc | 下一条用户消息
~~~

第一份请求的输入末端有机会形成可复用前缀。实际命中受供应商规则、消息渲染和缓存有效性影响。A 生成 ccc 的上下文独立，ccc 首次进入快模型时作为新增内容处理。使用现有用量记录区分快入口、工作和维护的实际调用与缓存量；架构按相同的实际请求前缀设计，不以 session ID 代替命中事实。

## 3. 按引用读取和交接

优先扩展现有工具，沿用 chatroom_read、works_list、work_get、work_create、work_dispatch、work_wait 和 work_notify。工具由接话模型在需要时调用。

| 动作 | 模型提供的参数 | 程序职责与回执 |
| --- | --- | --- |
| 读群消息或会话 | 目标房间或已有会话、关键词或记录位置、读取范围 | 核对调用者与来源范围，返回有界原文片段、作者、真实引用和游标。复用房间按 ID／游标读取和会话历史读取。 |
| 创建工作 | 目标、执行器或已有工作目标的选择、证据引用、必要说明 | 从当前已接收消息取得真实来源，保存 work 和动作记录，然后走对应执行器。返回 workId 和真实受理状态。 |
| 续跑工作 | 已有 workId、所选证据引用和增量说明 | 找到原工作和绑定，取回本轮用户原话与相关证据，按顺序投递。回执标明受理或失败。 |
| 登记等待 | 要等待的事件或外部结果；必要时补充后续说明 | 保存持久等待，结束本段占用。程序按已知工作和绑定续接；后续语义需要判断时交回相应模型。 |
| 发布工作结果 | 当前工作范围内由执行方写好的面向用户文本和来源 | 按已授权的来源和消息关系排入发布，返回真实投递状态。 |

接话模型可以直接读取 B 的一段原文，选出 B#28，调用「续跑 A」并附上解释。程序向 A 交付三类可区分的材料：

1. 本轮原始用户要求。原话保存在 S1，程序从真实消息取回全文或授权的精确片段。
2. 模型选中的证据。按房间消息 ID、会话条目或已有材料引用读取原文。较长内容传所选片段和剩余原文的指针。
3. 模型生成的交接说明。它描述需要采用的材料、当前问题和建议。原作者和来源保持可见，群消息、工具输出和其他模型的说明保留其证据身份。

消息引用由服务端解析并核对访问范围。单条引用不完整或不可用时保留能取得的材料，并把缺口作为普通信息交给模型处理。当前调用者、来源、回发目标和执行权限来自已接受的请求及已有工作关系。工作输入和结果输出都按其授权范围取材。向模型暴露有界的读取工具；同 Bot 下的会话仍按房间、工作及用户可访问来源确定读取范围。

改动入口主要是 bot/src/context/context.mjs 的 historyTool、bot/src/capabilities/core-tools.mjs、bot/src/capabilities/task-policy.mjs，以及 capabilities/gateway/tools.mjs 与 capabilities/services/builtin.mjs 的相应工具定义和执行入口。保持参数形状和授权边界清楚，让模型组合这些动作。

对现有 work_create 来源去重和 afterToolCall 的交接终止规则一起调整。一个已记录的持久动作使用同一事件／操作 ID 续办；一条消息确有多个独立授权动作时可以分别登记。快模型在完成资料读取和持久交接后结束本轮，仍有同轮内容时按工具回执继续。可选受理文案由模型随工具调用提供，实际保存成功后发布。

## 4. 工作执行、等待和结果回流

### Pi 和 Codex 路径

- Pi work 沿现有工作调度器和自己的 session 执行。常态输入为该任务已保存的上下文加本轮新要求、相关未读变化和证据。实际工具调用与结果保留在任务范围。
- 明确交给 Codex 的新工作先写入 work 和稳定提交操作，再由程序接入现有 Codex Desktop 能力。使用已选定且授权的项目目标。普通的直接委托可以从接话工具进入这条路径。
- Codex 续跑按 workId 找回已记录的 host、threadId 和已确认回合，只向原线程送本轮新增材料。复用 capabilities/codex/desktop.mjs 的原线程创建、续发、状态、独占操作与回执恢复。工作历史继续由该执行器持有。
- 同一 work 保持串行或沿已有运行引擎支持的追加要求机制处理，新消息在已确认的安全边界进入原任务。已发送但结果未知的副作用沿原操作查询。对已完成任务的明确新要求可以续接原 work；暂停、取消或停止后的晚到事件仍作为事实记录。

### 异步衔接

同步读取 B 时，快模型在本轮读结果并调用 A。B 需要另外执行时，程序保存来源消息和要等的 B 结果。已有 A 的绑定且后续动作明确时，收到对应事件即可投递；其他情况把可用结果交给负责判断的模型。模型可以用普通文字说明后续目标。比如 B 有三条辅助引用，第二条找不到，A 仍收到用户原话、第一和第三条以及一行缺项说明，继续用原会话工作。B 自身执行失败时也交回已有产出和真实状态，由负责模型判断能先做什么。复用 work_wait、工作事件和通知记录表达这种等待。

### 结果发布

目前 bot/src/runtime/bot.mjs 会把房间工作通知作为 work_result 再送入前台模型。改成由工作方写好可发布文字，程序沿已有 work_notify、通知记录和房间回复关联直接发布。以已保存的通知 ID 作为去重标识；未送达的通知仍在原记录中重试。

Codex 结果由连接器依据程序保存的实际线程、回合和操作记录匹配，接收该回合普通的最终回复及可用产物引用。保留原始执行观察，区分「提交已受理」「本次执行结束」「任务完成」「仍需输入」「结果未知」。没有专门摘要时可以使用普通答复；拿不到可确认的最终文本时，以实际可知的状态和来源回传。确实需要组合多份结论的请求才指定模型合成公开答复。

程序以真实事件更新用户可见的进度。A 的工具调用及私有材料留在 A；公开结果按原来源追加到主线。该结果是公开记录和证据，可以成为下一轮对话输入。已决定的结果投递无需再触发一次默认接话。

每个受理动作保存唯一来源和动作身份；自动续作、等待唤醒与外部回执沿实际因果关系继承。同一个 work 的另一条请求不会替代这个来源。无法确定来源的动作或通知留在待处理记录中，不猜测最新消息。执行 worker 不提供 work_dispatch；前台已完成的调度话语保留为材料，worker 只执行交付给自己的当前步骤。显式结果已有通知且没有新的实际动作时，收尾复用原通知。

跨工作等待中，明确的目标 A、依赖 B 和后续说明构成待交接步骤，即使可选 mode 写成 observe，也保留该步骤；仅等待同一动作结果时不追加执行。唯一已受理 taskId 可用于补齐缺省目标，显式错误目标仍拒绝。依赖结果到达后，输入分别保留原话、交接说明和历史，并突出当前步骤及已到达的实际 observation；失败和部分输出按原要求交给 A，成功前置条件仍须满足。

主要改动在 bot/src/runtime/bot.mjs、bot/src/runtime/works.mjs、capabilities/codex/desktop.mjs 和房间发布路径。复用现有 work、前后台调度位置、操作记录、外部订阅和恢复机制。按回复关联定位 A 时使用原绑定；普通自然语言仍由收到消息的模型解释。

## 5. 一次性提醒

在现有 Bot 管理能力中提供一次性提醒动作，复用现有 gateway 定时 tick 和房间发布入口。工具输入为相对延时或明确到期时间、提醒正文。程序根据真实请求取房间、Bot 和源消息，解析并存储到期时间，给出提醒 ID 与保存回执。相对延时以本轮消息接收时刻为基准。

持久记录含提醒 ID、源消息、发送目标、到期时间、正文和投递状态。到期后由程序以稳定消息 ID 发回原房间，成功后记为已送达；重启后处理仍待投递的到期提醒。取消和重试沿同一条记录。普通工作正在运行不占用这条通知的投递位置。

capabilities/bot-management/service.mjs、routines.mjs 和 gateway 工具注册是对应入口。已有周期职责按其原有事件类型执行；一次性提醒的到期动作是发布保存好的文字。

## 6. 记忆、压缩和上下文补充

沿用现有 3+3 数据分工。S1 保存原始消息、工具调用、回执和产物引用；S3 保存工作目标、进展、等待、绑定与通知状态；S2 Markdown 持有知识与总结的唯一正文，数据库保存目录、修订、处理位置和来源指针。项目规则按项目范围使用，任务发现留在所属范围，通用偏好有明确来源和适用范围。

| 需要时机 | 启动的短对话 | 输出和后续使用 |
| --- | --- | --- |
| 工作产生有价值的新事实、用户纠正或明确可复用的做法 | 整理 | 读取相关 S1、S3 和现行 Markdown，写更新或确认无需变更。可复用且已有依据的操作方法可以形成 Skill。 |
| 上下文接近窗口，需换一个安全起点 | 压缩 | 产出当前范围的恢复摘要、证据指针和覆盖位置。以摘要、其后的原文和实际工作状态开始新上下文代次。 |
| 跨来源筛选或旧任务恢复确实缺材料，现有模型的按需查询不足 | 组装 | 产出本次需要的资料、原文引用和必要说明，追加到本轮。 |

每次按自己的条件新开短对话，完成即结束。复用 bot/src/context/maintenance.mjs 的 shortDialogue、写入串行、修订检查和游标。收到实质事件可以把它标为待整理，结果发布和普通接话可以先完成。成功写入后推进相应游标，期间来的新原话保留为下一批。用户更正和停止要求当轮直接进入业务处理。

维护对话的普通 Markdown、文本和可用结构化内容都可作为材料。来源、范围和修订尽量由程序附上，可选信息缺失时使用能读懂的部分。写入边界检查文件归属和版本，生成的文字无需经过另一个审查模型，也不会因格式问题阻塞接话或已有工作。

减少 engine.mjs 启动前的默认语义组装。普通查历史、加载既有摘要和按 ID 追加材料由程序直接处理。只有缺口确实需要理解才起短对话。在两次上下文重建之间保留已用的前缀；新知识按需作为后续材料读取。压缩与整理保留原始记录和真实回执，恢复时依据已有操作状态。

例如排序工作结束后，程序先把本次修改结果送给用户。A 当前完成情况进入 S3，原文和回执进入 S1。若群里确认的排序规则值得长期沿用，后续整理对话把规则和原文引用写进对应的项目 Markdown。三个输出各自供后续读取。

## 7. 制作顺序和交付边界

1. 先接通干净主线输入与直接结果发布。保留公开消息的 ID 和边界，临时处理留在本轮。让 ccc 回到房间后自然进入下一轮快请求。
2. 扩展现有读取和工作工具，打通按引用交接、Pi 独立执行、Codex 直启与续跑。同步调整权限、交接终止、去重与等待，保证同一 work 沿原绑定处理。
3. 接入一次性提醒的保存、到期发布与重启恢复。普通接话进度改用真实执行事件。
4. 调整记忆维护触发、稳定前缀和必要时的上下文重建，整理与结果回流独立运行。
