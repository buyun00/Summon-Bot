# Summon Bot 桌面原生界面迁移方案

设计提案，2026-11-26。盘点基于仓库 0.5.30（build 201）的网页入口、事件处理和 Electron 桌面接口。目标是让普通网页、Windows x64 和 macOS arm64 使用同一份页面源码。网页先定稿，两端随后编译成原生界面。现有 iOS 和 Android 是可以借用实现经验及资源的独立客户端。[版本基线](../release.json) · [现行开发与发行方式](DEVELOPMENT.zh-CN.md)

## 哪些要分别做，哪些只写一次

平台侧实现文本编辑、滚动、绘制、窗口等基础能力。会话行、消息气泡、订阅表单、额度卡、详情抽屉以及它们组成的页面都可以只写一份。现有网页大量通过 JavaScript 拼 HTML、读 DOM 尺寸和委托点击事件，第一次需要把每个在用的页面迁成共享描述。此后调整布局或用已有组件加页面，只改共享源。引入新的系统交互或绘制能力时，才扩充两端控件库。[网页入口](../web/frontend/index.html) · [消息气泡的现有实现](../web/frontend/app.js#L4047)

## 如何使“网页定稿”直接成为构建输入

建议增加一个共享的 `ui/` 源目录，分开放页面／组合组件、颜色字号等设计值，以及无 DOM 依赖的状态与动作模块。页面用有类型约束的组件描述，支持槽位、条件、带稳定 ID 的循环、数据绑定和具名动作。现有 Node 构建工具把描述生成为网页 DOM、Windows 的 WinUI 视图和 Mac 的 SwiftUI 视图。生成的页面随各自产品编译，人工维护共享源和少量平台控件。

拟将共享组合与页面分别放在 `ui/components/` 和 `ui/pages/`，状态与动作放在 `ui/state/`。`desktop/windows/`、`desktop/macos/` 各自只维护平台控件与宿主，生成器放在现有 `scripts/build/`。构建遇到未实现的控件、动作或属性时，应指出引用它的页面和字段，方便一次补齐两端映射。

以下是聊天页的描述示意。输入栏本身也可以由附件按钮、原生文字输入和发送按钮组合。

```text
双栏布局（侧栏宽度＝侧栏宽度设置，窄窗策略＝折叠侧栏）
  会话列表（数据＝可见会话，选中时＝切换会话）
  纵向布局
    消息时间线（数据＝当前会话消息，行模板＝消息气泡，撑满剩余高度）
    工作状态条（显示条件＝当前会话有活动，点击＝展开执行抽屉）
    输入栏（文本＝本会话草稿，提交＝发送消息，拖入＝添加附件）
```

把状态条挪到输入栏下面，只需移动共享描述中的一行。像“上翻时保持阅读位置”这样的行为，由列表控件公开的滚动规则表达。网页制作阶段调整的是设计值和描述，三个目标会读到相同的变更。

**页面动作也只维护一份。** 建议把现有 JS 的去重、分页、分组、校验、发送状态、节点树布局等提取成无 DOM 的模块。浏览器直接运行这些模块。桌面用已经随包的 Node 运行同一模块，通过仅属于当前应用的标准输入输出管道与原生窗口交换具名动作和有稳定 ID 的变化项。首屏传一次快照，后续传增量。控制进程重启或序号中断时重新取快照。桌面会多一个随窗口退出的控制进程，使用现有 Node 二进制，无须再分发一份 JS 引擎。输入组词、选区、滚动、画布手势和逐帧动画都在原生控件内完成。[现有发送逻辑](../web/frontend/app.js#L750) · [可提取的快照合并逻辑](../web/frontend/cache.js#L66) · [本地运行时打包](../scripts/build/build.mjs#L120)

**沿用现有数据协议。** 共享动作通过现有本机或中枢 HTTP／SSE 接口访问数据，沿用协议握手、回执与重连。按节点、房间及当前历史批次隔离状态。切换电脑时丢弃前一请求迟到的界面更新。消息超时保留原 clientId，重试先查回执。草稿、选中项和未确认发送属于客户端。模型配置、工作区授权、对话和工具记录仍由原服务负责。[协议与事件流](../web/frontend/app.js#L1172) · [会话草稿](../web/frontend/app.js#L1387) · [中枢多节点](../web/frontend/hub.js#L175)

## 迁移顺序和每一步交付物

| 批次 | 具体工作 | 本批交付 |
| --- | --- | --- |
| 1 · 打通一张整页 | 建共享目录与三个生成目标。先做基础布局、文本、按钮、列表、折叠和主题。最小原生宿主接入现有正式实例，同步把 Token 用量的数据动作与页面分开。生成的网页资源同时接入本机 Web 和中枢的资源表 | 同一份用量页生成网页、Windows、Mac，支持切换周期、按 Bot／群查看及分页。此后调整指标卡顺序只改一处 |
| 2 · 迁日常聊天 | 迁工作台、会话侧栏、建群、聊天、输入栏和工作状态条。先落地滚动锚点、中文组词、带原 clientId 的发送与重试，再接 @、引用、附件、问答与执行抽屉 | 两个桌面原生目标能进入当前会话、查看历史、发消息、处理提问、拖入附件并追踪 Bot 工作。手机已有原生实现可用于核对语义 |
| 3 · 迁管理和文件表单 | 共用表单、弹窗、菜单、检查状态和图片预览。迁五项设置、群／Bot 详情、资料引用、模型接入、中枢账号和隐私输入。更新卡此时接入平台能力接口 | 网页定稿的表单、模型用途表、订阅和授权状态直接生成两端界面。资料引用能区分工作区活文件与普通附件，敏感提交只向界面返回脱敏结果 |
| 4 · 迁画布、品牌动画和首启 | 提取总览数据树、布局和绘制指令，两端接入原生视口和纸片头像素材。把完整开箱、模型接入、Bot 引导及进入工作台的阶段连起来 | 在原生画布定位群、执行、资料和记忆，支持缩放、展开和查看详情。首次安装能从开箱走到实际工作台 |
| 5 · 切换正式桌面发行 | 原生宿主接管应用身份、菜单、会话、更新和打包，按下节处理用户状态。接通现有 `release:desktop` 及同提交的 Actions 任务，移除已替代的 Electron 运行引用和打包依赖，随交付更新仓库桌面端约定 | Windows x64 可覆盖现有安装并从应用内更新。macOS arm64 提供签名公证 DMG 手动覆盖。日后网页定稿后从同一份源构建桌面，再依既有流程发布 |

### 发行切换与包体

- **升级覆盖。** 沿用 `org.lin0.relay.desktop`、Relay 用户配置位置、Windows 安装识别信息和 Mac 签名身份。首个原生版本需能被现有 Windows 自动更新入口发现并启动安装，新版接续自动更新。Mac 保持原应用标识和 Developer ID 公证的 arm64 DMG。发行先查本机，再查 GitHub。本机 Windows 包发到本机发行目录，GitHub 双桌面包由 Actions 从同一提交构建。[桌面打包](../desktop/build.mjs#L62) · [发行流程](CLIENT_RELEASES.zh-CN.md) · [客户端 Actions](../.github/workflows/client-releases.yml)
- **数据接续。** 使用现有正式服务和有效业务数据。原生版覆盖安装时，从旧 Relay 配置一次性迁入草稿、回复／提及／引用、暂存附件、待确认发送及其 clientId、已读位置、侧栏文件夹、外观和本地用户资料。暂存附件需要取出原文件内容或可持续访问的文件句柄。导入按原记录 ID 可重入，成功落盘后再清理被替代的客户端存储。直接从当前发行版升级也应覆盖此路径。可重建的服务快照按当前历史批次重新同步，本机会话按原鉴权流程续接。[客户端会话结构](../web/frontend/app.js#L1387) · [浏览器缓存](../web/frontend/cache.js#L164) · [侧栏组织](../web/frontend/app.js#L3230)
- **包体口径。** 现有 Windows 安装包为 135.9 MB，macOS DMG 为 168.9 MB。Windows 包内压缩数据估算约 110 MB 属于桌面壳及配套，约 25 MB 属于 Node、Bot、工具和 Web 服务。建议 Windows 优先复用共享 Windows App SDK。首次缺少运行库时，安装器补齐依赖并计入首次下载量。若要在这类机器上完全离线首装，必需依赖应随同一个安装包交付并计入包体。完整包仍提供本机 Bot 和供其他设备访问的网页。两端原生包容量以正常发行构建为准，分别列安装包和首次额外依赖即可。[Windows App SDK 分发方式](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/deploy-overview) · [Mac 发行记录](https://github.com/buyun00/Summon-Bot/releases/tag/client-macos-arm64)

建议第一批只交付 **Token 用量整页和它真正用到的基础控件**。第二批立即做消息列表和输入框，尽早解决最容易造成 Windows 与 Mac 体验分叉的滚动、中文输入以及发送回执。
